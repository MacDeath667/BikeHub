# Подготовка к закрытой бете

Реализовано в `engineering/dumb-implemnent`:

- Аккаунты, велосипеды, записи, комментарии, лайки, закладки, подписки и участие в сообществах хранятся в PostgreSQL через EF Core.
- Редактирование и мягкое удаление своих материалов; проверки владельца выполняются сервером.
- Профиль: имя, уникальный ник, город, описание, аватар с выделением области. Удаление аккаунта находится в настройках и требует отдельного email-кода.
- Сообщества: создание, аватары, список участников, посты, обсуждения и ответы; каталог загружается страницами по 20.
- GPX и ручные точки маршрута, карта на обложке записи без фотографий; форматирование текста и встроенные фотографии.
- Постоянные уведомления и @упоминания, приватные серверные черновики с локальным восстановлением, поиск людей и материалов.
- JPEG/PNG/WebP: до 10 МБ / 24 мегапикселей, максимум 1600 px, удаление метаданных, вывод WebP. Неопубликованные фото видит только владелец. Фотографии скрытого или заблокированного контента не публикуются, если не используются другим видимым материалом.
- Лимиты фото: 50 загрузок в сутки и 250 МБ на аккаунт. Изменяющие HTTP-запросы ограничены 60 в минуту на пользователя/IP в каждом процессе API; это не распределённый лимит.
- Жалобы, скрытие материалов, блокировка с отзывом сессий. Модераторы назначаются конфигурацией по подтверждённой почте, а не через клиент.
- Миграция добавляет таблицы/колонки через raw SQL `IF NOT EXISTS`, не удаляет прежние данные. Старые демонстрационные данные из памяти не переносятся.
- Compose сохраняет фотографии в `media-data`; NAS использует PVC `<auth-key-claim>-media`, отдельно для staging и production.

## Настройки

`Media:RootPath` — каталог фотографий. По умолчанию `App_Data/media` в каталоге API; в контейнере `/app/data/media`.

`Moderation:ModeratorEmails` — список email. Для локального Compose можно добавить `Moderation__ModeratorEmails__0` в environment API. В Ansible укажите `bikehub_moderator_emails: ['moderator@example.org']` в собственных переменных. Добавляйте только доверенные подтверждённые аккаунты.

При публикации через Nginx Proxy Manager обновите Custom Location по `infra/nginx-proxy-manager/bikehub.conf`: лимит тела запроса должен пропускать фотографию вместе с multipart-обёрткой. Изменение файла не применяет настройки панели автоматически.

## Ещё до приглашения пользователей

- Создать и смонтировать отдельный dataset NAS, заменить `bikehub_backup_root: /dev/null` и **проверить восстановление реальной серверной копии**. [Команды и recovery после прерывания](backups-nas.md) подготовлены; синтетическое восстановление проверено в CI. Том Docker/PVC сам по себе не является резервной копией.
- Проверить staging по публичному пути, отправку реальных писем, назначить модератора и провести ручную приёмку с двух аккаунтов.
- Подготовить политику обработки данных, согласия, контакты поддержки и политику хранения резервных копий. Вопросы размещения данных и подтверждения телефона для запуска в РФ остаются открытыми; эта ветка их не решает.
- Очистка неиспользуемых фотографий и удаление аккаунта по отдельному email-коду реализованы; границы удаления почты и резервных копий описаны в [документации](groups-and-account-deletion.md).
- При нескольких узлах API перейти с локального PVC на общее файловое/объектное хранилище. Реплики на одной VM могут пользоваться текущим томом; распределённые лимиты пока не реализованы.
- Уведомления об ответах, комментариях, подписках и упоминаниях реализованы; серверная выкладка ожидает доступа к NAS. [Описание](notifications.md).
- Автосохранение постов и обсуждений, локальное восстановление и защита от перезаписи между вкладками: [черновики](drafts.md).
- Общий поиск людей, записей, сообществ и обсуждений, а также фильтр внутри сообщества: [поиск](search.md).

Рабочий production и Nginx Proxy Manager в рамках этого этапа не обновлялись.

## Проверка этапа

- [CI коммита `d556b44`](https://github.com/MacDeath667/BikeHub/actions/runs/43898879204) прошёл все четыре job: 88 тестов API, 45 почты/операторских инструментов, 40 frontend-тестов, сборки .NET/TypeScript и проверки Ansible. PostgreSQL и Kafka — одноразовые, без рабочих данных.
- Штатная Docker-сборка web из исходников проверена после настройки npm. Собран и проверен отдельный .NET-контейнер операторских инструментов; libpq-файлы имеют права `0600`, каталог — `0700`, пароль отсутствует в connection-файле.
- `ansible-playbook infra/tests/staging.yml`: изоляция схем, ресурсов и томов staging проверена без подключения к NAS.
- Локальный Compose: регистрация с письмом в Mailpit, загрузка PNG с перекодированием в WebP, создание велосипеда и записи. После пересоздания API сессия, материалы и фотография сохранились. Тестовая сессия завершена; проверочные материалы оставлены локально с названием «Проверка…».
- 16 ноября: дополнительный прогон двух одноразовых аккаунтов — приватные черновики/фото, публикация с маршрутом, комментарий, группа, вступление, обсуждение, ответ, уведомления и четыре типа поиска. После перезапуска API сессия и черновик сохранились. Одноразовые аккаунты и пустая группа удалены; реальные письма не отправлялись.
- Локальный backup v2 и изолированное восстановление обеих БД, media, ключей и Kafka проверены; [границы серверной готовности](backups.md) остаются открытыми.
- NAS recovery entry point проверен в CI на синтетическом формате v3: две БД со схемами `public`, `mail`, `staging`, файлы обоих контуров и два изолированных брокера Kafka. Повреждённый mail dump отклоняется до создания ресурсов. Это не проверка реальных NAS PVC или dataset.

OrbStack пользователь останавливает вручную; автоматически его не запускать. Локальный стенд был обновлён и проверен до остановки Docker. Актуальная работоспособность выключенных контейнеров не заявляется. Визуальную мобильную приёмку пользователь выполняет самостоятельно; browser use отключён.

Локальная доводка продолжается независимо от NAS. Дополнительные DOM-тесты проверяют маршрутизацию поиска, retry неудачной страницы без потери загруженных карточек, устранение дубликатов, защиту от пропуска страниц и независимость загрузки поста от комментариев. Все 45 frontend-тестов и production-сборка прошли; контейнерные проверки выполняются в CI.
