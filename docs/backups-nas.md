# Резервные копии NAS

Сценарии предназначены для существующей одноузловой K3s VM. Ansible запускается с рабочей станции и подключается к VM по SSH. PostgreSQL остаётся внешним сервером. Нужны установленный на VM Docker, доступ к реестрам образов и отдельный dataset NAS, смонтированный внутрь VM. 16 ноября 2026 доступ к домашней сети восстановлен; dataset/NFS подготовлены и проверен реальный снимок обоих контуров.

## Настройка места хранения

В `infra/ansible/inventory/group_vars/bikehub/main.yml` заданы:

```yaml
bikehub_backup_root: /mnt/bikehub-backups
bikehub_backup_dataset: FileTrash/bikehub-backups
bikehub_backup_client_ip: 192.168.0.49
bikehub_backup_quota_bytes: 68719476736
```

`FileTrash` — отдельный от VM-диска на `Applications` пул. Новый dataset имеет квоту 64 ГБ без резервирования всего объёма, сжатие LZ4 и приватный корень `root:root 0700`. NFS экспортирует только этот dataset и допускает только VM `192.168.0.49`; `maproot` сохраняет права root для записи приватных файлов. Другие exports и dataset не изменяются. Запись через NFS и повторное применение проверены на реальном NAS; mount сохраняется в `fstab` VM с `nosuid,nodev,noexec`.

Подготовка и повторное применение:

```sh
ansible-galaxy collection install -r infra/ansible/requirements.yml
ansible-playbook -i "192.168.0.49," -u ansible \
  --private-key ~/.ssh/truenas_admin \
  infra/ansible/playbooks/prepare-backups-nas.yml \
  -e bikehub_target_group=all
```

Playbook работает с TrueNAS API по SSH под `truenas_admin`, без паролей или API-ключей в аргументах. Он отказывается менять чужой dataset без маркера `bikehub:purpose=backups` и заменять посторонний mount/скрывать существующие файлы. [Поля dataset API](https://api.truenas.com/v25.10/api_methods_pool.dataset.create.html) и [ограничения NFS export](https://api.truenas.com/v25.10/api_methods_sharing.nfs.create.html) дополнительно сверены с API установленного TrueNAS 25.10.6.

`bikehub_backup_root: /dev/null` по-прежнему служит выключателем: backup откажет **до SSH**, остановки сервисов и чтения Secrets. Данные в `/dev/null` не записываются. Backup требует уже смонтированную внешнюю файловую систему; каталог на системном диске VM не подходит. Если NFS был недоступен при загрузке VM, повторно выполните подготовку mount до backup.

Dataset создаёт `prepare-backups-nas.yml`, а `backup-nas.yml` только использует mount. Новый dataset наследует отсутствие шифрования от родительского пула; шифрование, хранение ключей и отдельная копия вне NAS настраиваются отдельно. Каталоги снимков имеют права `0700`, артефакты — `0600`. Они содержат персональные данные, ключи сессий, почтовые задания и Kubernetes Secrets. Нельзя публиковать их в Git или CI artifacts. Старые копии автоматически не удаляются.

## Создание копии

Из корня репозитория, после настройки dataset:

```sh
ansible-playbook -i "192.168.0.49," -u ansible \
  --private-key ~/.ssh/truenas_admin \
  infra/ansible/playbooks/backup-nas.yml \
  -e bikehub_target_group=all
```

Сначала собирается только образ существующего `BikeHub.Tools` для преобразования Npgsql-настроек в приватные файлы libpq, загружается клиент PostgreSQL, проверяются PVC, соединения с БД и конфигурация Kafka. Секретные значения остаются на VM: `kubectl` передаёт строку подключения непосредственно в stdin одноразового контейнера. Ansible-контроллер получает только имена, пути и контрольные суммы.

Перед остановкой writers сохраняется журнал исходных реплик `/opt/bikehub/backup-active/state.json`. Сценарий останавливает API и почту обоих присутствующих контуров, ждёт завершения их pod, записывает позиции почтовых топиков и корректно останавливает Kafka. Затем копирует БД и файлы PVC. PostgreSQL, web, nginx и Mailpit не останавливаются, но **API обоих контуров недоступен на время копирования**. В `always` сначала возвращаются исходные реплики брокеров с ожиданием готовности, затем API и почты. Никакие образы приложений не обновляются.

Полный каталог `<bikehub_backup_root>/<UTC-время>/` содержит:

- `database.dump`, `mail-database.dump` и инвентаризацию числа строк всех прикладных схем, включая `staging`. Если два Secret указывают на одну БД, оба dump содержат её полностью: схемы не разрезаются и данные других схем не пропадают.
- `auth`, `media`, `kafka` и аналогичные `staging-*` архивы фактически подключённых PVC с контрольными суммами файлов. Отсутствующий staging пропускается.
- `kafka-offsets.txt`, `staging-kafka-offsets.txt`, версии образов и cluster ID для проверки брокеров.
- `runtime.json`, `kubernetes.json` и `secrets.json`: исходные реплики, конфигурация namespace и только Secrets, на которые ссылаются выбранные приложения. Приватный JSON не выводится в логи и не передаётся на рабочую станцию.
- Архив `tls`, если существует управляемый каталог сертификата основного BikeHub. Сертификаты staging можно пересоздать; внешняя конфигурация Nginx Proxy Manager, его сертификаты, Grafana и сам TrueNAS сюда не входят.
- `manifest.json` формата 3 с SHA-256 каждого артефакта. Он записывается последним; каталог без него — незавершённая копия.

Другие программы не должны изменять эти БД, Kafka и файлы во время копирования. `server.yml`, `staging.yml` и `configure-mail.yml` проверяют блокировку; параллельные ручные `kubectl`/Docker-команды ей не управляются. Копирование рассчитано на один Kafka broker каждого контура и local-path PVC существующей VM.

## Если выполнение оборвалось

При обычной ошибке Ansible сам пытается вернуть исходные реплики. Если оборвался SSH/процесс Ansible или выключилась VM, после восстановления связи выполните:

```sh
ansible-playbook -i "192.168.0.49," -u ansible \
  --private-key ~/.ssh/truenas_admin \
  infra/ansible/playbooks/resume-backup-nas.yml \
  -e bikehub_target_group=all
```

Запускайте recovery только после завершения или остановки исходного backup-процесса. Команда проверяет root-private журнал, останавливает только Docker-помощники с меткой этого запуска и возвращает записанные реплики брокеров и приложений. Временные libpq-файлы удаляются. Журнал и блокировка исчезают только после успешного восстановления. Команда не читает значения Secrets, не разворачивает новые образы и не требует смонтированного dataset. Если копирование оборвалось до создания журнала, writers ещё не останавливались и снимается только пустая блокировка.

## Проверка восстановления

Подставьте полный путь завершённого снимка **на VM**:

```sh
ansible-playbook -i "192.168.0.49," -u ansible \
  --private-key ~/.ssh/truenas_admin \
  infra/ansible/playbooks/restore-check-nas.yml \
  -e bikehub_target_group=all \
  -e bikehub_backup_directory=/mnt/bikehub-backups/UTC-TIMESTAMP
```

Сначала сверяются все артефакты. Затем создаются новые одноразовые Docker volumes и PostgreSQL без сети и открытых портов. Восстанавливаются обе БД, сравнивается число строк каждой прикладной таблицы, извлекаются архивы и проверяются хеши файлов. Kafka поднимается из восстановленных данных отдельными изолированными брокерами с loopback-listeners; сверяются позиции топиков. Восстановленные API и почтовые потребители не запускаются, письма не отправляются. Secrets проверяются по хешу, их значения не импортируются в K3s. Временные контейнеры и volumes удаляются в `always`; исходный snapshot сохраняется.

Это проверка читаемости и согласованности копии, **не переключение работающего сайта** и не полная тренировка восстановления утраченной VM. Для реального аварийного восстановления сначала нужны чистая VM/K3s, внешний PostgreSQL и закрытая процедура восстановления конфигурации, ключей и данных. Автоматической перезаписи существующего контура здесь нет.

CI выполняет этот же entry point на синтетическом снимке с двумя БД, `public`/`mail`/`staging`, файлами обоих контуров и Kafka. Отдельно проверяется отказ до создания ресурсов при повреждённом mail dump.

## Проверка на реальном сервере

16 ноября 2026 создан снимок `/mnt/bikehub-backups/20261116T200923926317Z`: backup завершился без ошибок, исходные реплики API/почты/Kafka вернулись в Ready, оба API отвечают `200`. `restore-check-nas.yml` восстановил обе БД и все выбранные тома, сверил число строк, SHA-256 файлов и позиции обоих Kafka; временные контейнеры и volumes удалены. Исходные сервисы при проверке восстановления не останавливались; почтовые consumers из копии не запускались.

На реальном кластере дополнительно проверен возврат реплик из журнала после прерывания. Ожидание остановки writers и брокеров исключает терминальные pod (`Succeeded`/`Failed`): старые объекты `Completed` не являются действующими writers и не должны удерживать backup.

Для Kafka на VM был повторно использован уже имеющийся образ из K3s вместо длительного скачивания в Docker:

```sh
sudo k3s ctr -n k8s.io images export --platform linux/amd64 - \
  docker.io/apache/kafka:4.0.2 | sudo docker load
```

Это перенос публичного образа, без runtime-данных контейнеров. Версия берётся из manifest копии; при восстановлении иной версии/архитектуры используйте соответствующий образ. Полное аварийное восстановление потерянной VM, ключи шифрования и внешняя копия NAS остаются отдельной работой.
