# Поиск

Поиск открывается из верхней панели или пункта «Поиск» в меню, в том числе на мобильном устройстве. Адрес `#/search?q=...&kind=people&page=1` можно сохранить или отправить другому участнику. Переключение типа результатов возвращает первую страницу, изменение запроса отменяет старую загрузку и не позволяет запоздалому ответу заменить новые результаты.

Доступны четыре раздела:

- **Записи** — заголовок и текст постов в бортжурналах, переход к посту, лайки и закладки.
- **Люди** — имя, неизменяемый ник и город; запрос `@ник` также поддерживается. Email и телефон не участвуют в поиске и не попадают в ответ.
- **Сообщества** — название и описание, переход в сообщество.
- **В сообществах** — заголовки и текст постов и обсуждений со ссылками на материал, сообщество и автора.

В сообществе есть отдельная строка поиска. Она фильтрует выбранную вкладку «Посты» или «Обсуждения», сохраняя ограничение конкретным сообществом. Фильтр отражается в адресе `#/community/{id}?q=...`; его можно сбросить.

Поиск ищет подстроку без учёта регистра, включая кириллицу. `%`, `_` и `\` обрабатываются как обычные символы, не SQL-шаблон. Запрос ограничен 200 символами; пустой глобальный запрос не перечисляет всю базу. Это поиск подстроки, без исправления опечаток и морфологии. Внешний поисковый сервер не требуется.

## API и видимость

`GET /api/search/{posts|people|communities|discussions}?q=...&page=1&pageSize=10` возвращает обычный `Page<T>` с `total`, `pageNumber`, `pageSize`, `hasMore`. Размер страницы — от 1 до 50. Изменения данных между запросами могут сдвигать страницы; при неизменных данных порядок устойчив за счёт второго ключа ID.

`GET /api/communities/{id}/entries?kind=2&q=...&page=1` сохраняет обычную пагинацию сообщества по 20 записей. Скрытые и удалённые материалы, записи из скрытых/удалённых сообществ, контент заблокированных авторов и посты скрытых/удалённых велосипедов исключаются на стороне БД. Черновики не участвуют. Реакции и подписки рассчитываются для текущего пользователя, поэтому ответы поиска имеют `Cache-Control: no-store`.

Коллекции не включают JSON маршрутов: возвращается только признак `hasRoute`, сам маршрут загружается при открытии материала. Для страницы записей сообщества авторы загружаются одним запросом, а не отдельным запросом для каждой карточки.

## Миграция и индексы

Миграция `20261116134814_PublicSearchIndexes` добавляет четыре частичных GIN-индекса на выражения поиска и индекс ленты `(group_id, kind, created_at, id)`. Таблицы определяются текущей схемой подключения, поэтому индексы production и staging изолированы. Повторное создание защищено `IF NOT EXISTS`.

Для индексов используется расширение PostgreSQL `pg_trgm`. Оно устанавливается один раз в БД в `public`; если уже установлено в другой схеме, миграция использует её класс операторов. Для первой установки требуются `CREATE` в БД и доступ к схеме установки либо предварительная установка администратором. Это штатное расширение PostgreSQL: [документация pg_trgm](https://www.postgresql.org/docs/current/pgtrgm.html).

Индексы создаются обычным `CREATE INDEX` в транзакции миграции перед обновлением API. Построение на больших таблицах может задерживать запись; серверная выкладка и время построения ещё не проверены из-за отсутствующего SSH-доступа к NAS. Новый код пока не выкладывался в production.

## Проверки

- `dotnet test BikeHub.sln --disable-build-servers -m:1`: тесты поиска проверяют видимость, приватные поля и черновики, Unicode, буквальные спецсимволы, ники, границы входных данных, пагинацию и фильтр сообщества. На 5 025 записях проверяется план с GIN-индексом и постоянное число запросов для страницы с 20 записями.
- `npm test --prefix Web`: DOM-тесты проверяют запоздалые ответы, retry, пустой запрос/страницу, безопасное отображение текста и сохранение запроса в ссылках пагинации.
- Визуальная проверка на реальном телефоне остаётся за пользователем; DOM-тесты её не заменяют.
