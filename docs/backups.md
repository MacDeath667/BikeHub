# Резервные копии и проверка восстановления

## Локальный стенд Compose

Из корня проекта с работающим Docker и установленным Ansible:

```bash
docker compose up -d --build --wait
ansible-playbook infra/ansible/playbooks/backup-local.yml
```

Копия создаётся в `.local/backups/<UTC-время>/`; путь выводится после завершения. В неё входят:

- `database.dump` — PostgreSQL custom-format dump БД API `bikehub_local`;
- `mail-database.dump` — отдельная БД почты `bikehub_mail`, включая очередь и статусы идемпотентной доставки;
- `media.tar.gz` — фотографии из фактически подключённого к API тома;
- `auth.tar.gz` — ключи сессий из фактически подключённого тома;
- `tables.txt`, `mail-tables.txt` — число строк в прикладных таблицах каждой БД, без содержимого записей;
- `kafka.tar.gz`, `kafka.sha256` — данные Kafka после корректной остановки брокера и контрольные суммы файлов;
- `kafka-offsets.txt` — позиции разделов текущего почтового топика без содержимого сообщений;
- `media.sha256`, `auth.sha256` — контрольные суммы отдельных файлов;
- `manifest.json` — версия формата и SHA-256 каждого артефакта. Он записывается последним: каталог без манифеста не считается завершённой копией.

Playbook требует работающие PostgreSQL и Kafka, запоминает API и почту, останавливает работавшие writers, снимает позиции почтового топика и корректно останавливает Kafka. Затем копирует обе БД и фактически подключённые тома. В `always` сначала поднимает Kafka с ожиданием готовности, затем только API/почту, работавшие до копирования. PostgreSQL, Mailpit и nginx не останавливаются; в период копирования API недоступен. Для этого режима не должны параллельно работать нативный API из Rider/`dotnet run` или другие программы, изменяющие эти БД, Kafka и файлы. В противном случае единый согласованный снимок не гарантируется.

Файлы приватные, каталог имеет права `0700`, артефакты — `0600`. Они содержат персональные данные, почтовую очередь и ключи сессий. `.local/` исключён из Git; копии нельзя публиковать в CI artifacts, облачных логах или коммитах. Формат не шифруется сам: для долговременного хранения нужен защищённый зашифрованный носитель/датасет и отдельные правила доступа.

Для другого каталога укажите абсолютный `bikehub_backup_root`:

```bash
ansible-playbook infra/ansible/playbooks/backup-local.yml \
  -e bikehub_backup_root=/absolute/private/backup-directory
```

## Изолированная проверка

Подставьте путь завершённой копии из вывода предыдущей команды:

```bash
ansible-playbook infra/ansible/playbooks/restore-check-local.yml \
  -e bikehub_backup_directory=/absolute/path/to/.local/backups/UTC-TIMESTAMP
```

Проверка сначала сверяет формат и все контрольные суммы. Затем создаёт одноразовую PostgreSQL **без сети и открытых портов**, с новыми томами под уникальным именем и отдельными БД для API и почты. `pg_restore` работает только через сокет внутри этого контейнера. Исходные БД и тома не подключаются. Архивы извлекаются в другие временные тома; сверяются число строк каждой таблицы и SHA-256 каждого файла. После проверки файлов Kafka запускается отдельным брокером той же версии с исходным cluster ID, без сети и открытых портов; клиент через loopback проверяет позиции почтового топика. API и потребитель почты к восстановленным данным не подключаются, поэтому письма не отправляются. При успехе и при ошибке временные контейнеры и тома удаляются в `always`. Сама резервная копия сохраняется.

Текущий формат — `formatVersion: 2`. Старые копии версии 1 содержат **только БД API**, media и ключи: отдельная БД почты и Kafka в них отсутствуют. Проверка версии 1 остаётся доступна с явным сообщением об этом ограничении. Для полноценной новой копии запустите backup заново. Mailpit как временный тестовый ящик не резервируется.

Проверка версии 2 выполнена 16 ноября 2026: восстановлены обе БД (включая 32 записи почты), media, ключи и Kafka; позиции топика совпали. Исходный локальный стенд после копирования вернулся в healthy. Проверены совместимость с версией 1, отказ до создания ресурсов при повреждённом `mail-database.dump` и возврат Kafka/API/почты после намеренной ошибки `pg_dump`; у неудачной копии нет манифеста завершения.

Эта команда проверяет копию, а не переключает работающий сайт на восстановленную БД. Автоматическое восстановление поверх существующего стенда намеренно отсутствует.

## NAS и границы готовности

Локальная копия на диске Mac/VM не защищает от потери этого диска. Для NAS нужно отдельно согласовать место хранения вне VM, шифрование, ротацию и проверить восстановление серверных данных. На 16 ноября 2026 пользователь находится вне домашней сети, поэтому SSH к VM недоступен; серверный backup/restore пока **не проверен**. Не использовать Compose-playbook против K3s/production: локальные и серверные окружения устроены по-разному.

По решению пользователя путь NAS вынесен в `infra/ansible/inventory/group_vars/bikehub/main.yml`: `bikehub_backup_root: /dev/null`. Это заглушка, при которой серверный backup должен отказывать до остановки сервисов или чтения Secrets. Dataset и его подключение к VM создадим после возвращения в домашнюю сеть; текущая настройка не означает существование внешней резервной копии. Локальные playbook используют свой каталог `.local/backups` и не читают этот NAS-конфиг.

Минимальный состав серверной копии: согласованные схемы API и почтовой очереди, фотографии, Data Protection keys и защищённая копия конфигурации/Secrets. Без ключей могут потеряться активные сессии и возможность расшифровать отложенные письма. Конфигурация, TLS и внешние учётные данные должны восстанавливаться по отдельной закрытой инструкции; здесь их значения не сохраняются.

Сроки хранения и уничтожение старых копий должны учитывать удаление аккаунта. Текущие playbook не удаляют предыдущие копии автоматически.
